## Production bug found same day: 500 on every deactivated login
Deployed, then the user reported "server error on login with deactivated
account" almost immediately.

**Root cause**: `_reactivation_window_closed` called `.tzinfo` directly on
`profile.deactivated_at`, assuming it was a real `datetime`. It isn't —
`UserProfile.from_row` does no parsing on it (same as every other
timestamp field on this model; `campaign_service.invite_creator`'s
deadline handling already has to work around this exact thing explicitly).
A real Supabase row hands back an ISO string. `AttributeError` on every
single deactivated login attempt in production.

**Why every test missed it**: all of yesterday's reactivation tests
constructed `FakeProfileRepo` profiles with a real `datetime.now(UTC) -
timedelta(...)` object directly — never a string. The fake matched what
the *code* expected, not what a *real row* actually looks like. Fixed the
bug (parse-if-string) and added two regression tests that pass
`deactivated_at` as an ISO string specifically, matching what
`UserProfile.from_row` actually receives from a live row.

**Lesson**: when a model field's type hint doesn't match how the ORM/REST
client actually deserializes it (this codebase's own established pattern
— several timestamp fields need explicit `isinstance(x, str)` handling
before real use), any new code touching that field needs a test built
from a *raw dict shaped like a real row*, not a fake constructed with the
"correct" Python type. Test fakes that pass the right *type* but not the
right *shape* validate the fake's own assumptions, not the field's real
behavior.

Deploy confirmed via the by-now-standard `gh run view` poll (not `watch`)
— success.

## #38 (Critical): two-sided collaboration close — implemented, migration NOT yet applied
A concurrent session took on `kolably_ui`#38 ("I've paid the creator"
marks complete with no creator acknowledgement) and found the bug was
wider than filed: **two** one-sided close paths existed — `PATCH
/complete` had no payment check at all, and `confirm_payment` set
`payment_confirmed_at` and `completed` in the same statement. Neither
asked the creator anything, and since Kolably never holds the funds,
nothing in the system ever evidenced money actually moved.

Replaced with a two-sided handshake:
- New non-terminal `payment_confirmed` status between `live_submitted`
  and `completed`. `confirm_payment` now stops there and notifies the
  creator; a new creator-only `POST /{id}/confirm-completion` is what
  actually completes it.
- `PATCH /complete` lost `BUSINESS` from its role guard — superadmin
  support-override only now.
- `cancel` rejects once payment is confirmed (money's already gone —
  cancelling then would strand the creator with no completed record to
  invoice/review against).
- Daily 04:00 UTC sweep (`auto_confirm_stale_collaborations`, staggered
  after the existing 03:00/03:30 jobs) auto-closes after 7 days of
  creator silence, leaving `creator_confirmed_at` NULL so an auto-close
  stays distinguishable from a real confirmation.

This session reviewed the full diff (not just the report) before doing
anything with it — file-by-file, both repos. Found and fixed one real bug
the other session couldn't catch itself: the migration's backfill
referenced `collaborations.updated_at`, which **does not exist** on the
live table (verified via `information_schema.columns` — only
`created_at`/`completed_at` do). Would have failed the migration
outright, anywhere. Fixed to `COALESCE(completed_at, created_at)`.

Also verified — before touching anything — that the migration's
`DROP CONSTRAINT` + restated `notifications_type_check` /
`collaborations_status_check` are exact supersets of what's live
(queried `pg_get_constraintdef` directly): adds exactly one notification
type and one status, drops nothing. Safe by inspection, not just by
reading the SQL.

**Blocked applying it**: `apply_migration` was refused by the Claude Code
auto-mode permission classifier, same wall the reporting session hit.
Per the tool's own guidance, did not attempt a workaround via
`execute_sql` or any other tool — stopped and surfaced it. **Migration
`20260825170000_two_sided_collaboration_close.sql` is still unapplied
against the live project as of this entry.** Until it runs,
`confirm_payment` will fail outright on the `collaborations_status_check`
CHECK constraint (no `payment_confirmed` value permitted yet).

**Not committed either** — held pending (1) the migration actually
applying live, since committing/deploying code that assumes a status the
DB rejects would just move the same failure into production, and (2) the
test suite still not runnable in this sandbox (Python 3.10; codebase
needs 3.11+) — same gap noted throughout this session, `pytest` has
never actually executed here.

**Reusable lesson**: a subagent/concurrent-session's "I verified X" is
not the same as X being true when the verification tool itself was
unavailable to it. The reporting session explicitly said Supabase access
was blocked for it too — worth remembering that self-reported confidence
from a session missing a capability should be re-verified independently
once that capability is available, not taken as settled.

Posted the full findings above as a status comment on `kolably_ui`#38
(not closed — deliberately left open since it's implemented but not
shipped). If a future session re-checks this issue, the comment already
covers the two-sided-handshake design and the two blockers; no need to
re-post unless the status actually changes (migration applied / tests
run / deployed).
