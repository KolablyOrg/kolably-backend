  `VITE_SUPABASE_ANON_KEY` were never configured as Vercel Environment

  User added them to Vercel and redeployed.

  `[notif-debug]` logging): `kolably_ui/vercel.json`'s CSP `connect-src`
  never listed the Supabase project origin, so the browser blocked the
  Realtime WebSocket outright (`CHANNEL_ERROR: transport failure`). Fixed
  by adding `https://uxngcuyrdmajydkqpiyi.supabase.co` and
  `wss://uxngcuyrdmajydkqpiyi.supabase.co` to `connect-src`. Committed
  `da310a2`, merged with unrelated concurrent mobile/README commits, pushed
  as `b7d034b`.
- Both findings written up in
  [[knowledge/references/kolably-ui-missing-supabase-env-vars]] — **this
  silently broke chat's live delivery too**, not just notifications; chat's
  REST resync fallback was masking it the whole time.

## Same day, later still: the retest surfaced a real design problem, not deploy lag

The deploy-gap theory above was correct as far as it went — but the user's
retest (after the fix was genuinely live) still failed, because the fix
itself was wrong in a way pure code/data review hadn't caught. User's exact
words: *"the api should return error message or something and not let me
go to OTP screen"*.

Root issue: the #31 fix stayed **silent** on purpose (anti-enumeration —
same generic success response for deactivated/active/nonexistent emails
alike), which meant a deactivated account's owner got sent to the OTP
screen exactly as if a code had been sent, except none was, so the screen
could never succeed — a dead end with zero explanation. Changed to an
explicit `403` instead, trading away that narrow enumeration protection for
a real, user-facing UX fix — full reasoning in
[[decisions/003-explicit-deactivation-error-over-enumeration-protection]].
Verified no frontend changes were needed (both `kolably_ui` clients already
throw-before-navigate + have working interceptor toast handling).

**Applied the lesson from the deploy-gap incident immediately**: pushed
`cbef5fe`, then actually watched the `Deploy Backend` run via `gh run
watch` instead of assuming success — per
[[knowledge/references/verify-deploy-via-github-actions]]. `gh run watch`
itself lost its connection partway through ("connection reset by peer")
and its exit code couldn't be trusted as-is — confirmed the real outcome
with a direct, separate `gh run view <id> --json status,conclusion`
instead of trusting the watch session's own exit status. Conclusion:
**success**, completed 16:43:35 UTC. Fix is confirmed live, not just
pushed.

## Lesson, stated plainly
Silent/non-leaking responses and clear user-facing errors are in direct
tension, and defaulting to one without surfacing the tradeoff to the user
is itself a mistake — should have flagged the anti-enumeration choice as a
call worth making explicitly *when the #31 fix first shipped*, not waited
for a confused bug report to discover the user wanted the other tradeoff.
