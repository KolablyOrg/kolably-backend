## Push notifications — backend half

Full writeup (design decisions, the `uv run pytest` discovery, mobile
side) lives in `kolably_ui`'s `logs/2026-08-29` — that's where this pass
actually started (a formal task list from the user covering both repos).
Backend-specific summary:

- New `push_tokens` table (migration `20260829120000_add_push_tokens.sql`,
  applied directly to the live project and verified — table + index
  present — before commit). Keyed unique on `expo_push_token` itself, not
  `(profile_id, token)`: a device re-logging into a different account
  should reassign its row, not orphan it.
- `push_notification_service.send_push_to_profile` — fire-and-forget,
  never raises, same contract as `notification_service.create_notification`.
  A response with `details.error == "DeviceNotRegistered"` deletes that
  token; any other error status leaves it (might still be valid next try).
- **The one call site**: `create_notification` itself now calls
  `send_push_to_profile` after a successful insert. All 17 existing
  triggers across `application_service`/`campaign_service`/`chat_service`/
  `collaboration_service`/`invoice_service` get push for free — none of
  them were touched.
- `POST`/`DELETE /notifications/register-token` added to the existing
  `notifications` router (already had `get_current_user` wired, natural
  home).
- Full suite run twice (`uv run pytest`, 381 passed both times) — once
  before merging in a concurrent session's unrelated Instagram/portfolio
  work, once after, to isolate whether any failure would've been mine vs
  theirs. `uv run ruff check .` clean too.

**Deploy verified**, two ways: `Deploy Backend` reported success, and
fresh prod logs (`Fetch Prod Logs`, not the one that fired alongside the
deploy) showed a clean new-container startup. Neither alone proves *this*
feature is live though — this deploy added no new scheduler job (unlike
the #38 collaboration-close feature, whose extra job was a visible
fingerprint in the startup log), so a container that merely didn't crash
isn't strong evidence the new routes exist. Confirmed directly instead:
`curl -X POST .../notifications/register-token` and the `DELETE` variant
both returned `401` (auth required) against production, not `404` — proof
the routes are actually registered on the running server, not just that
old code kept working. **Worth remembering as a pattern**: when a change
adds no scheduler job or other passive startup signal, a targeted
unauthenticated curl against the new endpoint (expecting 401/422, not
404) is a fast, concrete way to confirm a deploy shipped the intended
code rather than just "didn't fail to boot."
