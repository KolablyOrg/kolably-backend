## Addendum: why push + live chat still didn't work (Cowork session)

User reported both halves still broken: no push when the app is minimised,
and chat not auto-refreshing ("do we not have websockets yet?"). Read the
existing vault first rather than re-deriving — most of the stack was
already built and correct, so the useful work was finding what was left.

**Root cause of "chat doesn't auto-refresh": mobile Realtime never starts.**
`mobile/.env` is missing `EXPO_PUBLIC_SUPABASE_URL`/`ANON_KEY`, so
`getSupabase()` returns null and every subscriber returns early. Full
writeup: [[knowledge/references/mobile-realtime-env-vars-missing]]. This is
the *same bug* as the web one documented on 2026-08-23 — that doc even said
"check this first for any other Realtime report," but the check was never
extended to mobile, which has its own `.env` and its own `getSupabase()`.
Notably this also means the presence rate-limit bug fixed earlier today
(`8205fd5`) — real, and worth fixing — could never have been the cause of
the missing live message on that device: the channel was never created.

**Root cause of "no push when minimised": Android delivery config.**
Two independent problems, both invisible (the send succeeds either way):
- The notification channel was created with `IMPORTANCE_DEFAULT`. On
  Android, channel importance — not the payload — decides whether a
  notification produces a heads-up banner. DEFAULT means tray-only, which
  reads as "nothing arrived."
- The Expo payload omitted `priority` and `channelId`. Without
  `priority: "high"` FCM may defer delivery while backgrounded/dozing;
  without `channelId` Android uses a low-importance fallback channel.

Fixed both. Used a **new** channel id (`messages_v2`, not `default`)
deliberately: Android freezes a channel's importance at creation time, so
installs that already created `default` at DEFAULT importance would be
stuck there forever — a new id gets a correctly-configured channel without
requiring a reinstall. Added a test asserting `priority`/`channelId`/
`badge`, since these are invisible in every other test (they don't affect
whether the request succeeds, only whether a human sees the result) and a
silent drift between the two constants would re-break Android push with no
error anywhere.

**Also built: mobile notifications Realtime.** The
`notifications:{profile_id}` broadcast topic has existed since
`20260823150000` and web has consumed it since — mobile never did, and
polled `getUnreadCount()` every 20s instead (the asymmetry flagged earlier
today under "surfaced while debugging"). Added
`mobile/lib/notificationRealtime.ts` + `hooks/useNotificationsRealtime.ts`
(mirroring `useConversationRealtime`'s reconnect/resync/app-state
discipline, minus presence), wired into `ChatUnreadContext` and the
notifications screen. Poll interval dropped from 20s to 120s and
re-framed as a fallback for exactly the case above — Realtime being
unavailable in ways the app can't detect.

**Verification honesty**: `uv run pytest` did NOT work in this sandbox,
contrary to the "reusable discovery" logged earlier today — `.venv` points
at a missing interpreter here and uv can't download one (network blocked).
So that discovery is **environment-specific, not universal**: it worked in
that session's sandbox, not in every one. Backend changes were
syntax-checked only; mobile typechecked clean (2 pre-existing unrelated
errors). Nothing committed.

## Addendum 2: both reports explained by screenshots the user sent

User sent a web screenshot + an iOS screenshot after the fixes above still
didn't work. Both causes were visible in the images, no further code
archaeology needed:

**"Live updates unavailable"** is rendered in the mobile chat header. Traced
it: `chat-thread.tsx` shows that string for exactly one
`connectionStatus` value — `'unavailable'` — which
`useConversationRealtime` sets in exactly one place, when `getSupabase()`
returns null. Re-checked `mobile/.env`: still zero `SUPABASE` lines. So the
env vars flagged in
[[knowledge/references/mobile-realtime-env-vars-missing]] were never added,
and the app is now literally displaying that fact on screen. (The
`connectionStatus` indicator itself was added by a concurrent session the
same day — good timing; it turned an invisible failure into a one-glance
diagnosis.)

**Push**: the iOS screenshot is the **Simulator** (iPhone 17 Pro / iOS 26.3
in the macOS Simulator chrome). `registerForPushNotificationsAsync` returns
null immediately when `!Device.isDevice`, so no token is ever registered and
the server has nothing to send to.

> **CORRECTION (same session).** I first concluded from this that "remote
> push cannot work on a Simulator at all" and told the user to go get a
> physical device. **That was wrong**, and it would have cost them a day.
> Checked Expo's actual docs after the user said "i am using expo":
> *"You can test push notifications on a physical Android or iOS device, on
> an Android Emulator with Google Play services, or on an iOS Simulator
> running on Xcode 14 or later (macOS 13+, iOS 16+)."*
> (docs.expo.dev/push-notifications/push-notifications-setup, updated
> 2026-07-28.) Their Simulator is iOS 26.3 — comfortably supported.
>
> So the blocker is **our own code**, not an OS limitation: the
> `if (!Device.isDevice) return null;` guard refuses to even attempt token
> registration on an environment where push works fine. Expo's own reference
> implementation has no such check — it calls `getExpoPushTokenAsync` and
> handles failure. Removed the guard; token acquisition is now attempted
> always and errors are caught and logged (an Android emulator without Play
> services is the genuine failure case that now lands there). Also added the
> `Constants.easConfig?.projectId` fallback Expo's reference uses — checking
> only `expoConfig.extra.eas.projectId` can miss it in a dev build.
>
> The `expo-device` dependency stays, but only to *report* the environment
> in diagnostics, never to gate behaviour.

**Two lessons, and the second is the important one:**
1. For "feature X doesn't work on my device" reports, establish *what the
   device is* first — it's visible in any screenshot with window chrome.
2. **A plausible platform-limitation explanation is the most dangerous kind
   of wrong answer**, because it closes the investigation and moves the
   blame outside the code. "Simulators can't do push" *was* true years ago,
   sounded authoritative, and matched the symptom perfectly — which is
   exactly why it went unchecked. Verify capability claims against current
   vendor docs before acting on them, especially when the conclusion is
   "nothing is wrong with our code."

### Built: user-runnable diagnostics instead of another round of guessing
User asked for "a demo push notification that can be called from the app" —
the right instinct, so built it properly rather than as a throwaway button.

- `POST /notifications/test-push` — sends to the caller's own devices only
  (no recipient param, so it can't push to anyone else) and **reports**:
  device count, Expo's per-token receipt, and a distinct message for the
  no-devices-registered case. Deliberately the inverse of
  `send_push_to_profile`'s contract: that one swallows everything (correct
  for production, useless for debugging), this one lets transport errors
  raise. A debugging tool that reports success on a failed request is worse
  than no tool. Tests cover all three branches.
- `app/push-diagnostics.tsx` — device/permission/projectId/token/Realtime
  state in one screen, plus two tests that split the path in half:
  **local** (device-only, works on Simulator — proves permission + handler +
  channel) and **server** (full path — proves delivery). If local works and
  server doesn't, the problem is delivery, not the app. Linked from both
  settings screens. Shows an explicit Simulator banner rather than letting
  someone burn another session on an impossible test.
